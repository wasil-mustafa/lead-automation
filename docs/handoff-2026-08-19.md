### 1. The "Enriching" sheet (`qa_artifact.py`)

A sheet in the QA workbook Stage 1 already produces. `ENRICHING_COLUMNS` are Salesforce field
API names; each row is **exactly** what `lead_field_payload` produces for one Lead, so a dry
run can be applied by hand: paste into Inspector Reloaded's Data Import (object Lead, action
Update, id field `Id`). Rows whose payload is only the `Id` are dropped, mirroring
`writeback.py:212`.

Not a workflow, not a mode, not a flag — every Stage 1 run has it. Tests:
`tests/test_qa_artifact.py::test_enriching_sheet_*`.

### 2. Vendored feed reader (`src/leadauto/_vendor/`)

CI could not read the kununu feed at all, in three independent ways, each sufficient alone and
all of which logged like success:

1. No `Main-Profile-Account` checkout, so `mpa_bridge` raised `MpaBridgeError` → caught → one
   warning.
2. The workflows passed `KUNUNU_API_TOKEN`, which `common.kununu_feed` refuses by design (the
   feed is HTTP Basic, not Bearer) — so even with a checkout the download was unauthenticated.
3. `actions/cache` named `kununu_profiles.jsonl`, a path nothing has written since kununu moved
   the feed to CSV on 2026-08-06.

Cost of that: no alt names (weaker LF match acceptance), no kununu industry (silently fell back
to LeadFeeder) and no `profile_score` — which fails the live-scope gate **closed**, so a live
scheduled run could not have converted anything even with `dry_run: false`.

Fix, Wasil's call after being shown the alternatives: a byte-identical snapshot of
`common/{__init__,kununu_feed}.py` at `src/leadauto/_vendor/common/`. The reader lives in a
private repo owned by another person, and the `GITHUB_TOKEN` Actions injects is scoped to this
repository; the alternatives were a **classic** PAT (fine-grained cannot reach another personal
account's repo at all) or a deploy key Nicolaus would have to add.

**This relaxes the global "import it, never vendor it" rule. The guards are the reason it is
acceptable — do not remove them:**

* The real checkout still wins. `common_kununu_feed()` falls back only when the checkout is
  *absent*, warns, and **appends** to `sys.path` so a real checkout keeps precedence.
* A checkout that is present but **broken raises** instead of falling back.
* `tests/test_mpa_vendor.py` hashes the snapshot against the live files (CRLF-normalised) and
  fails on drift. It skips where Main-Profile-Account is absent, so it fires on the laptops that
  hold both repos.
* A test pins why only two files were copied: `kununu_feed` imports nothing from its package but
  `REPO_ROOT`.

Never edit the copies. Fix upstream, then re-sync per `_vendor/PROVENANCE.md`.

## The incident — every workflow was invalid for ~50 minutes

`071f4c1`–`ac670e2` put this in a **job-level** `env:` block:

```yaml
    env:
      KUNUNU_CACHE: ${{ runner.temp }}/kununu/profiles.csv
      HAS_MPA: ${{ secrets.MPA_PAT != '' }}
```

Neither the `runner` nor the `secrets` context exists at job level, which makes the entire file
invalid. GitHub reports that as a **0-second `startup_failure`** — no job, no log, and no
annotation retrievable through the API, so the runs look like an unexplained flake.

* `enriching.yml` broken 09:18 UTC, **`stage1.yml` 09:32**, `backtest-skipped.yml` 09:39.
* Every push created three red runs. The 12:00 Vienna scheduled dispatch was lost.
* Fixed by reverting in `b05198c`; env needing `runner`/`secrets` now sits on the **step**.

Runs to look at if you want the evidence: `32238107580`, `32238754865`, `32239782752`, and the
dispatch `32240424178`.
